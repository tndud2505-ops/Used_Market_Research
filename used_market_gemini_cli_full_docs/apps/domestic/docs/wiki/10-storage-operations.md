# 저장 공간과 장기 통계 운영

최종 운영 결정: 2026-10-04. USED WEB만 대상으로 한다. KSTOCK 파일·Docker·로그·스케줄과 공유 서버 전체 정리는 대상이 아니다.

## 무엇을 오래 보관하는가

오래 축적할 자료는 **확정된 가격 결과**다. 원자료와 복구용 복사본의 보관 기간을 가격 이력에 적용하지 않는다. 일별 평균만으로 과거 기간 전체의 중앙값이나 중복 제거 표본 수를 재구성할 수 없으므로, 확정된 기간 통계도 그대로 보존한다.

| 자료 | 정책 | 구현·보호 |
| --- | --- | --- |
| 날짜별·출처별 최종 통계 | 자동 기한 삭제 없이 축적 | `daily_price_stats`, `daily_source_price_stats`, 날짜 범위 유지. 평균·중앙값·최솟값·최댓값·표본 수·버전 유지 |
| 확정된 전체 기간 통계 응답 | 최근 30일은 기존 형식, 이전 결과는 무손실 압축하여 축적 | `gzip-json-v1` + 원문 SHA-256. 현재 활성·가장 최근 게시본 보호. 조회 시 검증·복원, 재계산 없음 |
| 원자료·관측 상세 | 현재 30일 통계 검증에 필요한 상세 보관 | 기존 최신 매물 snapshot, 분류 교정·중복 판정 근거 보호. 정상 표본 임의 삭제 금지 |
| 수집 실행 로그 | 기존 35일 | 정기 통계 게시 후 기존 원장 정리 |
| 일일 DB 백업 | 7일 안의 최근 3개 날짜 | 24시간 지난 백업 무손실 gzip. 유효한 마지막 복구본은 오래되었다는 이유만으로 삭제하지 않음 |
| 수동 SQLite 복구 백업 | 최대 7일 | 더 최신인 7일 이내 일일 백업의 복구 검증이 성공한 경우에만 만료. `.keep` 및 활성 참조 보호 |
| 완료된 게시 staging | 완료 후 최소 7일 | `publication-status=complete`, AWS 검증 영수증, 원장 게시 ID·행 수 일치가 모두 필요. 현재·최신 게시 작업 보존 |
| 미완료·실패·증거 없는 staging | 자동 삭제 제외 | 완료 또는 포기 근거를 먼저 확인. 날짜나 폴더 이름만으로 완료로 간주하지 않음 |
| 코드·환경·교정 근거 파일 | SQLite 자동 만료 대상 아님 | 코드 백업에 DB 전체 복사를 섞지 않는다. 비밀 환경 파일은 출력·Git 저장 금지 |

현재 공개 조회의 최대 기간은 기존 730일이다. DB 이력의 자동 삭제를 없앤 것과 공개 조회 기간을 늘리는 것은 별개다. 필요한 원자료가 정리된 과거 결과는 저장된 확정값으로 읽는다. 원자료 없는 재계산이나 일평균들의 단순 평균으로 과거 대표가격을 대체하지 않는다.

## 매일 실행되는 작업

- 기존 03:00 KST 통계 게시가 성공한 뒤 DB 백업과 30일 상세 정리를 수행한다. 이 경로에서 오래된 통계 응답을 압축한다. 장애 복구 목적으로 전체 과거 재계산을 실행하지 않는다.
- `used-market-backup-storage.timer`가 매일 **06:30 KST**에 별도 정리를 실행한다. Runner와 Tunnel 재시작 없이 동작한다.
- 백업 삭제 전에 가장 최신 생존 복구본을 SQLite `quick_check`로 검증한다. gzip은 압축 해제 CRC와 원문 체크섬도 확인한다. 검증 실패·사용 중·공간 부족이면 해당 삭제를 진행하지 않는다.
- 압축은 1MiB 버퍼를 사용하며 압축 해제 결과와 원문 SHA-256이 같아야 원본을 교체한다. 중단 후 원본과 `.gz`가 함께 남으면 내용이 동일할 때만 중복을 해소한다.
- 정리 서비스는 낮은 CPU/I/O 우선순위, 메모리 최대 128MiB, 단일 실행 잠금을 사용한다. 실제 서비스의 수집 메모리와 별도다.

상태와 실제 실행 결과:

```bash
systemctl status used-market-backup-storage.timer used-market-backup-storage.service --no-pager
journalctl -u used-market-backup-storage.service -n 40 -o cat --no-pager
```

타이머 활성화만으로 정리가 완료된 것은 아니다. 해당 실행의 `action=complete`, 서비스 `Result=success`, `ExecMainStatus=0`을 확인한다. `recovery_check_started`만 있고 종료 기록이 없으면 아직 복구 검증 중이다.

## 작업자가 지킬 최소 규칙

1. 큰 백업·배포 전 `node /opt/used-market-runner/aws-runner/backup-storage-policy.mjs`를 실행한다. DB+WAL 크기에 추가 1GiB 또는 20% 중 큰 값을 남긴다. 검사 시점의 여유 공간이지 미래 사용량의 예약은 아니다.
2. 코드 변경에 매번 전체 DB를 복사하지 않는다. 검증된 일일 백업을 재사용하고, 범위 교정에는 필요한 범위의 복구 근거만 남긴다. 새 전체 복구본이 꼭 필요하면 공간 검사와 동일한 보관 정책을 적용한다.
3. 진행 중이거나 해결되지 않은 복구 자료는 해당 폴더의 `.keep` 또는 해당 백업의 `<파일명>.keep`으로 보존한다. 정리가 검토할 수 있도록 이유를 짧게 기록하고 복구 종료 후 해제한다.
4. 백업 복원·이동은 `/var/lib/used-market-runner/backups/.storage-maintenance.lock`에 `flock` 잠금을 잡고 수행한다. 완료된 staging을 재사용해 쓰지 않는다. 새 작업 경로를 사용한다.
5. staging 완료 표시는 실제 게시 영수증과 원장 저장이 확인된 뒤에만 기록한다. 실패 작업에 성공 영수증을 만들거나 경과 시간만으로 완료 처리하지 않는다.
6. 운영 DB `VACUUM`, 서비스 중단, 유효 표본 삭제는 자동 공간 정리 수단으로 사용하지 않는다. 소유자가 불명확한 파일·공유 Docker는 건드리지 않는다.

정리 계획을 먼저 확인할 때:

```bash
sudo python3 /opt/used-market-runner/aws-runner/maintain-backup-storage.py --daily
```

실제 기존 정책 실행:

```bash
sudo systemctl start used-market-backup-storage.service
```

만료 예외는 조용히 성공으로 숨기지 않는다. `*_kept`, `*_skipped`, 실패 이유와 대상 경로를 보고한다. 복구본이 오래되었다면 먼저 정상 일일 게시·백업 경로를 복구한다. 오래된 마지막 복구본을 지워 보관 일수만 맞추지 않는다.

자동 정리에서 제외된 실패·검증용 작업은 주간 용량 확인 때 함께 검토한다. 후속 작업으로 대체됐다는 실행 기록과 미사용 상태가 확인되면 해당 임시 DB의 정확한 경로만 정리하고, 판단 근거는 작업 기록에 남긴다. 이때 자동 정리 조건을 맞추기 위해 가짜 게시 성공 영수증을 만들지 않는다. 해결되지 않은 복구본의 `.keep` 이유도 함께 확인해, 필요성이 끝난 예외가 계속 쌓이지 않게 한다.

## 하네스와 배포

- `npm run test:storage`: 백업 공간 계산, 같은 날짜 백업 재사용, 복구 백업 보호, 설치 연결 검증. Linux에서는 아래 Python 계약도 실행한다.
- `sudo python3 harness/backup-storage-contract.py`: 실제 임시 SQLite 파일로 압축 왕복, 손상된 복구본, 잘못된 날짜, 경로·sidecar·pin 보호, 7일 수동 백업 및 성공 staging 정리를 검사한다. Windows에서는 `/proc`·`fcntl`이 없어 이 부분을 Linux에서 별도로 실행한다.
- `harness/pc-stored-price-publication-contract.mjs`: 2년 이상 지난 자료 정리 후 날짜별·출처별·기간 통계 수치 보존, 압축 복원 및 재실행 안전성을 검사한다.
- 전체 `scripts/verify.ps1` 또는 `scripts/verify.sh`에 연결되어 있다.
- 정상 Runner 설치는 `install-backup-storage.sh`를 함께 실행해 타이머를 설치한다. 현재 저장소의 기본 운영 경로 `/opt/used-market-runner`만 지원한다.

새 압축 형식을 쓰기 전에 압축을 읽을 수 있는 Runner 코드를 먼저 배포해야 한다. 옛 코드로 롤백할 때 압축 해독 모듈을 제거하면 과거 조회가 깨진다. 현재 독해 호환 모듈을 유지한 코드 롤백 또는 검증된 DB 복구본을 사용하는 복구 계획이 필요하다. 배포·복구마다 현재 실행 중 수집·게시 및 내부/외부 Runner 인스턴스를 확인한다.

## 용량 판단

2026-10-04 관측에서 최근 전체 통계 1회는 약 121MB JSON이었다. 원문 상태로 매일 보관하면 연간 약 44GB다. 같은 게시본 300행의 압축 표본은 원문 대비 약 6%였고, base64와 포장 메타데이터를 포함한 DB 보관 크기는 그보다 크다. 모든 제품과 미래 수집량의 압축률을 보장하는 수치는 아니다.

이 정책은 큰 중복 백업과 임시 자료의 누적을 제한하고, 통계 성장 속도를 줄인다. 장기 확정 통계와 매물별 보호된 최신 자료는 계속 성장한다. 따라서 영구적인 고정 용량을 보장하지 않는다. 실제 월별 DB·백업·staging 증가와 여유 공간을 분리해 확인하며, 복구본 한 개를 추가로 만들 공간을 항상 남긴다. 공유 서버의 전체 여유 변화와 USED WEB 자체 회수량을 같은 값으로 보고하지 않는다.
