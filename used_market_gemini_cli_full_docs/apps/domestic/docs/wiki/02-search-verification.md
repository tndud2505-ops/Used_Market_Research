# 사이트별 검색 검증

마지막 갱신: 2026-08-21
상태: 코드·fixture 계약과 운영 live·브라우저 검증 완료

## 현재 운영 검색 정책

사용자에게는 `추천`, `낮은 가격`, `높은 가격`, `최신` 네 가지 기준을 제공한다. 첫 검색은 사이트별 최대 160개 후보를 검증해 사이트별 최대 160개, 전체 최대 640개를 AWS SQLite 색인에 저장한다. 화면은 PC·모바일 모두 30개씩 보여준다.

검색어·카테고리·처음 선택한 사이트 묶음은 하나의 검색 세션이다. 전체 검색 뒤 사이트 탭을 바꾸면 `view_sites`로 같은 스냅샷을 필터링해 먼저 응답하고, `focus_sites`와 `collect_view=true`로 선택 사이트만 320개 후보까지 보강한다. 보강 응답은 30개씩 3페이지, 최대 90개를 미리 읽어 사용자가 3페이지로 이동할 때 추가 대기를 줄인다. 사이트 보기와 정렬은 수집 키를 바꾸지 않지만 커서는 보기 조건별로 분리한다.

브라우저는 전체 스냅샷과 사이트별 응답을 별도 상태로 보존한다. 특정 사이트 보강이 끝난 뒤 다른 사이트로 바꿔도 직전 사이트 전용 배열을 다시 필터링하지 않고 전체 스냅샷의 해당 사이트 결과를 즉시 보여준다. 따라서 탭 전환 중 `0개`로 깜빡이지 않으며 서버의 `index_view` 응답이 도착하면 실제 총량과 커서를 교체한다.

`낮은 가격`은 현재 브라우저에 있는 결과 배열을 숫자 가격 오름차순으로 즉시 바꾼다. 이어 서버에서 같은 SQLite 스냅샷의 전체 후보를 가격순으로 조회해 첫 30개와 커서를 교체한다. 이 과정은 `collect_view`나 원 사이트 `price_asc` 수집을 호출하지 않는다. 가격이 없거나 표시용 가격인 항목은 마지막으로 보낸다.

`높은 가격`도 같은 SQLite 스냅샷을 숫자 가격 내림차순으로 조회하며 원 사이트 재수집을 호출하지 않는다. 사이트 탭에서 전체로 돌아가도 `price_desc`와 가격 범위를 그대로 전달해 0개로 초기화하지 않는다.

페이지 번호는 전체 페이지 수를 알려주되 이미 내려받은 페이지와 바로 다음 페이지까지만 버튼으로 제공한다. 예를 들어 1/34페이지에서 `34`는 총량 정보일 뿐 클릭 버튼이 아니며, `다음`은 cursor 한 번으로 2페이지만 읽는다. 마지막 페이지에서 수집 창을 넓힐 때도 별도 `다음 매물 더 찾기` 문구를 쓰지 않고 항상 `다음`으로 표시한다. 사이트 보강 중에는 중복 확장을 막고, 보강이 끝나면 번호 페이지를 다시 활성화한다.

저장 색인이 있으면 경과 시간과 함께 먼저 표시하고 서버가 주는 `poll_after_ms`를 1~20초 범위로 적용해 최근 매물 확인 결과를 최대 3분 동안 확인한다. 첫 페이지에 머물면 자동 반영하고 다른 페이지에서는 업데이트 버튼을 표시한다. 6시간이 지난 색인도 `stale`로 명시해 먼저 제공하고 백그라운드 갱신을 예약한다. 캐시가 전혀 없는 첫 검색만 원 사이트 수집을 기다린다.

첫 색인 생성 때는 원 사이트별 최신 후보 창을 수집한다. 이후 가격 범위·정렬 응답은 SQLite에서 즉시 만들며, `낮은 가격` 진입이나 결과 확장도 원 사이트 가격순 경로를 사용하지 않는다. 사이트 탭 진입과 `다음 매물 더 찾기`만 선택 사이트의 최신 후보 창을 보강한다.

`낮은 가격`은 가격이 1차 정렬 기준이다. 위험 매물을 앞에서 몰래 삭제해 진짜 최저가까지 사라지게 하지 않고 `가격 확인` 경고를 붙인다. 다만 필수 필드 누락, 명백한 카테고리 불일치, 중복, 사이트별 최저 가격 미만, 신선도 기준 초과는 제외한다. 가격 이상 판단의 중앙값은 여러 카테고리를 한 번에 검색해도 카테고리별 표본으로 계산한다.

SQLite와 live 병합 모두 숫자 가격을 첫 정렬 키로 사용한다. `price_suspect`·`quality_suspect`·사기 위험도는 같은 가격 안의 보조 키와 사용자 경고일 뿐, 더 비싼 정상 매물을 더 싼 주의 매물보다 앞세우지 않는다. 가격이 없거나 표시용 가격만 있는 항목은 마지막으로 보낸다.

`최신`도 가격·신선도 필터를 우회하지 않는다. 날짜가 없는 C2C 매물은 삭제 대신 품질 경고를 받고 날짜가 확인된 최신 매물 뒤로 간다. 리씽크몰은 소매 재고 특성상 날짜 누락 경고의 예외다.

### 2차 속도 정책 최종 검증

- 1차 기록의 원 사이트 가격순 보강은 폐기했다. UI와 Worker 모두 가격 정렬을 이유로 원 사이트 가격순 수집을 시작하지 않는다.
- `npm test` 전체 통과: UI 페이지네이션 40개, 검색 세션 정책 41개 포함
- `npm run index:harness` 통과: 색인 117개, cursor 31개, 운영 계약 19개, 통합 25개, UI 신선도 13개
- Worker 하네스 141개, Cloudflare 릴리스 하네스 40개 통과
- 운영 브라우저에서 `아이폰 15` 전체 검색 505개를 표시한 뒤 중고나라 기존 2개를 약 1.1초 안에 먼저 표시하고 307개로 보강했다.
- 중고나라 3페이지는 30개를 약 1.6초 안에 표시했다. 낮은 가격순은 약 1.2초 안에 20,000원부터 오름차순으로 표시했다.

- 운영 모드는 `cache_first`, Worker 버전은 `db115350-8c3f-4a8e-aeda-d1c19a76c66e`다.

### 2026-08-21 페이지네이션·반복 전환 회귀 검증

- `1/34페이지`에서 34페이지 직접 이동이 중간 cursor 33개를 순차 요청해 모든 버튼이 오래 비활성화되는 문제를 재현했다.
- 먼 페이지는 숫자 정보만 표시하고, 현재 내려받은 페이지와 바로 다음만 버튼으로 제공하도록 변경했다. `다음 매물 더 찾기`는 제거하고 모든 진행 버튼을 `다음`으로 통일했다.
- 로딩 해제 코드가 `이전`·`다음`의 정확한 disabled 상태를 덮어쓰던 문제를 제거했다.
- `높은 가격순`으로 사이트 → 전체 전환할 때 Worker가 `price_desc`를 거절하던 문제를 수정하고, SQLite 내림차순 cursor를 추가했다.
- 회귀 하네스: UI 페이지네이션 50개, 검색 cursor 39개, cache-first 통합 32개, live 검색 143개, 검색 세션 42개 통과. `npm test`, `npm run index:harness`, Cloudflare 45개 계약도 통과했다.
- 운영 브라우저 반복 흐름 통과: 전체 1,000개 → 2·3페이지 → 중고나라 → 낮은 가격 → 10만~30만원 → 높은 가격 → 전체 → 번개장터 → 최신 → 헬로마켓 → 리씽크몰 → 전체 → 초기화.
- 전체 복귀 후 높은 가격은 30만원부터 내림차순, 가격 필터 해제 후 전체 1,000개가 복원됐다. 콘솔 오류·경고는 0건이었다.
- AWS 실패 시 사용하는 D1 백업 검색도 `price_desc`와 최소·최대 가격을 허용하며, 가격 없는 항목을 마지막에 두고 내림차순으로 반환한다.
- 가격 범위 응답이 끝나면 진행 상태를 즉시 닫아 정렬 버튼이 정상적으로 다시 활성화됐음을 화면에 반영한다.
- 운영 모드는 `cache_first`, Worker 버전은 `61544219-71da-488f-b150-403d7abc45b4`다.

## 카테고리 클릭과 통합 검색의 공통 규칙

카테고리 목록은 `market/logic/category-catalog.ts`의 canonical ID를 단일 기준으로 사용한다. 화면에 보이는 카테고리와 실제 수집 경로가 따로 놀지 않도록 사이트별 요청은 다음 순서로 계획한다.

1. 요청한 canonical 카테고리와 일치하는 확인된 소스 카테고리 ID가 있으면 해당 공식 카테고리 페이지를 조회한다.
2. 세부 ID가 없고 확인된 부모 카테고리만 있으면 계획 메타데이터에 `parent_fallback`으로 남기되 선택·조회는 막고 회색으로 표시한다.
3. 공식 ID가 전혀 없으면 카테고리명을 검색어로 사용하는 계획만 기록하고, 사이트별 카테고리 클릭은 비활성화한다.

키워드 fallback은 결과를 그대로 카테고리 상품으로 확정하지 않는다. 상품명에서 다른 canonical 카테고리로 분류되는 결과는 제외하고, 남은 결과도 `inferred`로 취급한다.

`GET /api/categories`의 `site_plans`는 화면 선택 가능 상태도 함께 제공한다. `availability: official`만 요청한 canonical 카테고리의 공식 ID로 선택 가능하다. `parent_fallback`은 상위 분류가 있다는 참고 메타데이터일 뿐 `selectable: false`로 회색 표시하며, `unavailable`도 동일하게 요청하지 않는다. 사이트 탭을 특정 사이트로 바꾸면 지원하지 않는 카테고리는 회색 disabled로 표시한다. 전체 사이트 탭에서는 선택한 카테고리를 지원하는 사이트가 하나라도 있을 때만 활성화한다.

다중 선택은 `POST /api/search`의 `category_ids`(최대 8개)를 사용한다. 서버는 카테고리명을 하나의 검색어로 뭉개지 않고 카테고리별로 조회한 뒤 canonical 원문 URL로 중복 제거·병합한다. 여러 카테고리의 다음 페이지는 `version: 2`의 `category_cursors` 안에 카테고리별 기존 사이트 cursor와 이미 노출한 `seen_items`를 보존해 외부 사이트의 상품 순서가 밀려도 재노출을 막는다. 부모와 자식 카테고리를 동시에 선택하면 화면에서 중복 조회를 피하도록 한쪽을 해제한다.

따라서 회색 비활성 카테고리를 클릭 요청으로 보내거나 `CATEGORY_COLLECTION_UNAVAILABLE`을 정상 0개처럼 보여서는 안 된다. 결과가 없을 때도 실제 조회 완료 후의 `결과 없음`인지, 공식 ID 미확인으로 비활성화된 상태인지 메타데이터와 경고로 구분한다.

카테고리 클릭과 통합 검색은 같은 canonical category ID와 같은 `resolveCategoryCollectionPlan()`을 재사용한다. 카테고리 분류가 공식 ID 기반인지 검색어 추론인지의 차이는 `category_confidence`와 `category_mapping_mode`로 분리한다.

회귀 계약은 `harness/category-contract.mjs`에서 모든 canonical 카테고리와 기본 사이트의 수집 계획을 확인하며, 실행은 `npm test`에 포함된다.

웹 요청 검증 실패는 500 내부 오류가 아니라 400 입력 오류로 반환한다. 원 사이트가 차단되거나 추출기와 응답 구조가 맞지 않는 경우에는 매물을 `0개`로 성공 처리하지 않고 사이트별 `확인 필요` 상태와 재시도/원문 확인 안내를 표시한다.

페이지네이션은 사이트별 계약을 따른다. 중고나라는 첫 페이지 다음에 `page:2`부터 사용하고, 번개장터 키워드 검색은 공개 API의 `page:1`부터 사용한다. 번개장터 공식 카테고리는 `slice:v1` 내부 위치와 공식 opaque cursor를 함께 보존한다. 헬로마켓·리씽크몰 원본 페이지를 모아 만든 결과도 AWS 스냅샷 커서로 30개씩 제공한다.

2026-08-12 live 확인에서 중고나라는 여성 바지 `1026`, 남성 바지 `1035`, 여성 상의 묶음 `1023/1024/1025`, 남성 아우터 묶음 `1030/1031` 등 공식 하위 ID를 사용하며 원문 이미지 URL까지 반환한다. 번개장터는 공식 MDMS 목록을 기준으로 의류·패션잡화·모바일·PC·가전·뷰티·유아동·가구·도서·티켓·스포츠·공구 등의 단일/복수 카테고리 ID를 사용하며, 카테고리 검색은 `pw.product.category` opaque cursor와 페이지 내부 slice 위치를 이어간다. 당근은 현재 공개 검색 응답의 증거 구조가 맞지 않으면 `UNSUPPORTED_EVIDENCE_SHAPE`로 표시하고, 일부 지역만 성공한 경우 부분 결과 경고를 표시하며, 판매 상태를 읽지 못한 매물은 `unknown`으로 둔다. eBay는 `EBAY_BROWSE_API_TOKEN` 미설정 상태에서 `CATEGORY_COLLECTION_UNAVAILABLE`과 토큰 설정 복구 경로를 표시하고, Browse API가 판매 상태를 제공하지 않는 경우 원문 확인 경고와 `unknown` 상태를 사용한다.
번개장터 매핑 ID는 코드에만 고정하지 않는다. `npm run bunjang:taxonomy`가 공식 MDMS 분류 목록의 하위 노드까지 펼쳐 우리 41개 매핑 ID의 존재 여부와 활성 상태를 확인한다. 이 검사는 외부 네트워크가 필요한 별도 운영 검증이며, 실패하면 해당 매핑을 공식 분류로 간주하지 않고 회색 비활성 후보로 재검토한다.

중고나라도 `npm run joonggonara:taxonomy`로 매핑된 공식 검색 URL을 일괄 요청해 HTTP 200 여부를 확인한다. 2026-08-12 확인에서는 36개 ID가 모두 200을 반환했다.

실제 웹 API 카테고리 회귀는 `npm run category:live`로 수행한다. 여성 바지 단일 조회, 여성 바지+모바일/태블릿 다중 조회, 공식 카테고리 ID가 없는 헬로마켓·리씽크몰의 검색어 없는 카테고리 제외 계약을 함께 확인한다.

공식 번개장터 카테고리 API는 카테고리 상품을 반환하지만 검색어를 함께 제한하지 않을 수 있다. 따라서 검색어가 명시된 경우 모델·핵심어 일치 필터를 추가하고, 카테고리만 눌렀을 때는 해당 카테고리 전체를 보여준다. 카테고리 선택 전 입력한 검색어도 단일·다중 선택 모두 유지한다.

명시 키워드와 카테고리를 함께 고른 경우 `keyword_is_explicit` 경계를 유지한다. 공식 카테고리 결과에도 키워드 필터를 적용해 모바일 카테고리에서 `RTX 5070` 같은 무관한 상품이 통과하지 않게 하며, 카테고리만 고른 경우에는 카테고리 라벨을 별도 검색어로 오인해 전체 결과를 버리지 않는다. `iPhone/아이폰`, `Galaxy/갤럭시`, `AirPods/에어팟` 등 공통 상품명 별칭은 중고나라·번개장터·검색 전용 소스에서 같은 방식으로 비교한다.

가격 이력은 요청 기간 안의 날짜만 사용하고 숫자 토큰은 부분 문자열이 아닌 토큰 단위로 비교한다. 따라서 `iPhone 15`가 `LGA1151 B365`의 `15`와 잘못 연결되지 않는다. 통화가 섞인 통합 결과의 가격 요약은 임의 환산하지 않고 `MIXED`로 표시한다.

헬로마켓·리씽크몰은 공식 카테고리 ID가 없는 검색어 기반 소스다. `/api/search`의 일반 키워드 검색에는 항상 참여하고, 명시 검색어+카테고리 검색에도 결과 분류 필터를 거쳐 참여한다. 검색어 없는 카테고리 탐색에서는 공식 카테고리처럼 가장하지 않고 제외된다. 레거시 `/api/search-only`는 안정적인 원본 cursor가 없어 단독 호출의 `limit`·`cursor`를 400으로 거절하지만, 메인 검색은 AWS 색인의 최대 1,000개 스냅샷에서 자체 cursor로 페이지를 제공한다.
