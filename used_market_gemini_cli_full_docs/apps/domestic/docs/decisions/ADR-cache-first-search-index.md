# ADR: 4GB AWS 캐시 우선 검색 색인

- 상태: 구현 완료, 2026-08-20 `cache_first` 운영 전환 결정
- 결정일: 2026-08-14
- 주 저장소: AWS 로컬 SQLite
- 장애 대체: Cloudflare D1의 최근 핵심 매물

## 사용자에게 보이는 의미

`색인`은 이전 검색에서 검증해 저장한 매물 목록이다. 같은 상품을 다시 찾거나 가격·정렬만 바꿀 때 원 사이트를 모두 다시 기다리지 않고 이 목록을 즉시 조회한다.

`최신 매물 확인`은 저장 결과를 먼저 보여준 뒤 원 사이트의 최근 1~2페이지를 확인해 신규·가격 변경 매물만 합치는 과정이다. 6시간을 넘긴 결과도 `stale`과 확인 경과 시간을 표시해 먼저 제공하고 백그라운드에서 갱신한다. 캐시가 전혀 없는 첫 검색만 원 사이트 수집을 기다린다.

## 확정한 구조

```text
브라우저
  → Cloudflare Worker
  → AWS Runner
      → SQLite 색인 즉시 조회
      → 최근 매물 백그라운드 확인
      → 신규·변경 병합
      → 변경분만 D1 백업
```

- 검색어는 NFKC·소문자·공백·특수문자·한영 별칭을 정규화한다.
- `아이폰15`, `아이폰 15`, `iPhone-15`는 같은 색인이다.
- `S24`, `M2`, `V10`처럼 한 글자와 숫자로 된 모델명은 원 사이트 검색에서도 붙여 보내며, `S 24` 입력도 같은 형태로 정규화한다.
- `아이폰15 프로`는 별도 색인이다.
- 가격 범위와 정렬은 색인 키에서 제외한다.
- 첫 검색은 사이트별 최대 160개 후보를 확인하고 품질 검증 후 사이트별 최대 160개, 전체 최대 640개를 저장한다.
- 원 사이트의 페이지 크기에 맞춰 요청 후보 수만큼 여러 페이지를 조회한다. 번개장터는 페이지당 20개로 초기 160개 후보에 최대 8페이지, 중고나라는 페이지당 50개로 최대 4페이지를 사용한다. 목표 수량 충족이나 원본 마지막 페이지에서는 즉시 중단한다.
- 번호 페이지를 누를 때마다 브라우저는 우리 서버에 다음 30개를 요청한다. 서버는 같은 검색 스냅샷의 커서를 조회하며 이 동작만으로 원 사이트를 다시 수집하지 않는다.
- 저장된 결과의 마지막 페이지에서는 `다음 매물 더 찾기`를 제공한다. 이 버튼만 원 사이트 수집 창을 사이트별 160→320→480→640개로 한 단계 늘리고, 검증·중복 제거 후 새 서버 스냅샷으로 교체한다. 확장 창은 검색어에 저장해 이후 깊은 갱신이 다시 160개로 줄지 않게 한다.
- 확장 시 번개장터·헬로마켓은 최대 32페이지, 중고나라는 최대 13페이지까지 확인한다. 브라우저에는 여전히 한 번에 30개만 보내며 한 검색 스냅샷은 전체 최대 1,000개다.
- 커서는 검색 조건·정렬·스냅샷 버전·마지막 정렬 키를 서명해 담는다. 프로세스 메모리나 서버 재시작에 의존하지 않는다.
- 한 검색 스냅샷은 최대 1,000개이며 6시간 보관한다. 단계 확장 수집과 전체 검증 결과도 이 상한 안에 고정한다.
- 스냅샷은 상품 표시값과 정렬값을 함께 고정한다. 갱신 중 가격이 바뀌거나 전역 상품 정리가 실행돼도 사용자가 넘기던 페이지의 총량·순서·가격은 변하지 않는다.
- 가격·정렬 변경은 브라우저의 현재 결과를 즉시 재배열한 뒤 `refresh_index=false`로 SQLite만 다시 조회한다.
- 가격·정렬을 바꾸면 기존 커서를 버리고 새 조건의 1페이지를 조회한다.
- 정렬 변경은 `collect_view`나 `acquisition_mode=price_asc`를 사용하지 않으며 원 사이트 수집·색인 쓰기를 발생시키지 않는다.
- 낮은 가격순은 숫자 가격을 첫 정렬 키로 사용한다. 의심·품질·사기 위험 표시는 같은 가격 안의 보조 키와 경고로 유지하고, 가격 없음·표시용 가격은 마지막에 둔다. 더 비싼 정상 매물을 더 싼 주의 매물보다 앞세우지 않는다.
- 품질 판정은 전역 상품이 아니라 `(정규화 검색어, 상품)` 연결에 저장한다. 같은 상품도 검색어가 다르면 액세서리·광고·모델 불일치 판단이 달라질 수 있기 때문이다.
- 교환 전용, 매입 요청, 박스·구성품만 판매, 본체·휴대폰 제외, 광고·가이드와 사기 위험도 0.45 초과 상품은 낮은 가격순 상단에서 제외하거나 가장 뒤 등급으로 보낸다. 경계값 0.45와 범위를 벗어난 위험도 값은 자동 고위험으로 단정하지 않는다.
- 6시간 이내 결과는 fresh, 이후 저장 결과는 stale로 표시하되 캐시 우선 응답을 유지한다.
- 최근 24시간 10회 이상은 인기 검색어로 15분, 2~9회는 일반 검색어로 60분마다 확인한다.
- 단발 검색어는 예약 갱신하지 않으며 다음 일반 검색에서 5분 이상 지났을 때 최근 매물을 확인한다.
- 7일간 검색되지 않은 검색어는 예약 갱신 대상에서 제외한다.
- 인기·일반 검색어는 24시간마다 깊은 재수집을 수행한다.
- 백그라운드 수집은 동시 1개, 시간당 12개다. 사용자 검색 슬롯을 우선 보존한다.
- Cloudflare의 AWS 검색 프록시 제한은 60초다. 초기 160개 깊은 수집이 15초를 넘더라도 중간에 D1 대체로 바뀌지 않고 AWS 검증 결과를 기다린다.

## 저장과 삭제

- SQLite는 WAL·FTS5·64MB page cache를 사용한다.
- 이미지 파일과 원본 HTML은 저장하지 않는다.
- 활성 상품은 100,000개, 검색어는 10,000개를 넘지 않는다.
- DB 750MB에서 압축 정리를 실행하고 1GB부터 백그라운드 쓰기를 중단한다.
- 성공한 깊은 수집에서 두 번 연속 사라지고 마지막 확인 후 6시간이 지나야 비활성화한다.
- 사이트 실패는 누락 횟수로 계산하지 않는다.
- 비활성 상품은 14일, 가격 변경 이력은 30일 또는 상품당 최근 10건을 보관한다.
- 온라인 백업은 하루 한 번 만들고 최근 3개만 유지한다.
- D1은 5개 사이트별 최근 2,500개, 전체 최대 10,000개를 변경분 위주로 보관한다.
- D1 용량·쓰기 예산은 [공식 한도](https://developers.cloudflare.com/d1/platform/limits/)와 [요금·무료 사용량](https://developers.cloudflare.com/d1/platform/pricing/)을 기준으로 운영한다.

## API 계약

- `POST /api/search`: 기존 요청을 유지하며 `freshness`, `refresh`를 추가한다.
- `POST /api/search`: 첫 30개와 `pagination.next_cursor`를 반환하고 다음 요청은 같은 스냅샷을 이어간다. 만료·구형 커서는 410이다.
- `GET /api/search/refresh/:token`: 진행 중 202, 완료 200, 만료 410이다.
- `GET /api/index/status`: 운영자 토큰이 필요하며 DB·디스크·메모리·갱신 지연·shadow 비교 수치를 반환한다.
- 화면은 확인 경과 시간, 최신 확인 중, 신규 매물 수를 표시한다.
- 첫 페이지는 완료 결과를 자동 반영하고 다른 페이지에서는 버튼을 눌러야 반영한다.

## 장애 경계

- 일부 사이트 실패: 성공한 사이트만 갱신하고 실패 사이트의 누락 횟수는 유지한다.
- 전체 원본 실패: 기존 색인 시각을 갱신하지 않고 오래된 결과를 별도 선택으로만 제공한다.
- AWS 실패: Worker가 D1의 제한된 최근 결과로 대체하며 실시간 결과로 표시하지 않는다.
- DB 750MB, 여유 디스크 2GB 미만, RSS 2.5GB, 검색어 등급별 갱신 간격 2배 초과를 경고한다.
- systemd는 `MemoryHigh=2560M`, `MemoryMax=3072M`로 제한한다.

## 단계적 활성화

아래 shadow 기준은 최초 도입 당시의 안전 전환 절차다. 2026-08-20 사용자가 검색 대기시간을 우선 개선하기로 결정해 `cache_first`로 전환하며, 품질 지표는 전환 차단 조건이 아니라 운영 모니터링·롤백 조건으로 유지한다.

첫 배포는 `RUNNER_INDEX_MODE=shadow`로 실행한다. 이 모드는 사용자에게 live 결과를 주면서 색인에도 기록하고, 성공한 사이트에 한해 live 대비 색인의 누락률·오래된 결과율을 기록한다.

shadow 비교는 사용자 페이지 크기와 무관하게 한 검색의 전체 수집 창인 최대 1,000개 색인을 조회한다. 상위 200개만 비교하면 DB에 이미 있는 하위 상품을 누락으로 오판하므로 전환 지표로 사용하지 않는다.

품질·정렬 로직을 배포한 경우에는 그 최종 배포 시각 이후의 비교 행만 전환 지표로 사용한다. 이전 계산식·진단 호출·배포 전 품질 결과가 24시간 누적값에 섞여 있어도 전환 근거로 인정하지 않는다.

`shadow`의 최초 검색은 기존 live 비교 경로를 사용한다. 다만 같은 검색 세션에서 `refresh_index=false`로 요청한 사이트 보기·정렬은 SQLite 스냅샷을 즉시 사용하고, 이어지는 `collect_view=true` 또는 `expand_index=true` 요청만 원 사이트를 수집한다. 이렇게 해야 탭 전환이 비교 지표를 불필요하게 늘리지 않으면서 선택 사이트 보강은 계속 live로 검증된다.

`shadow`의 live 페이지 창은 5분간 유지한다. 백그라운드 색인 갱신은 사용자가 넘기고 있는 live 페이지 창을 삭제하지 않는다. `cache_first` 전환 뒤에는 6시간 SQLite 스냅샷과 `index:v2` 커서가 이 역할을 대신한다.

최초 계획은 24시간 뒤 다음 조건을 확인한 뒤 `RUNNER_INDEX_MODE=cache_first`로 바꾸는 것이었다.

- 비교 실행 30회 이상
- 5개 사이트와 주요 카테고리 검색 포함
- 누락률 5% 이하
- 오래된 결과율 10% 이하
- DB·디스크·메모리 경고 없음
- 전체 원본 실패가 새 갱신으로 기록되지 않음

전환은 `/etc/used-market-runner/runner.env`의 모드만 변경하고 서비스를 재시작한다. 전환 뒤 DB·디스크·메모리 경고, 신규 검색 실패, stale 비율 급증이 확인되면 `shadow`로 되돌리고 사이트별 수집·정규화 원인을 수정한다.

## 2026-08-17 운영 대상 변경

- 운영 검색 대상은 중고나라·번개장터·헬로마켓·리씽크몰 네 곳이다.
- 당근은 동일 공개 검색에서 지역 파라미터를 바꿔도 같은 결과가 반복돼 사용자 지역을 증명할 수 없으므로 제외한다.
- 과거 당근 포함 검색어는 갱신 대상에서 격리하고, AWS SQLite와 D1의 당근 상품은 정리한다.
- 휴면 수집 어댑터는 회귀 자료로 남길 수 있지만 공개 API·화면·스케줄러에서는 호출하지 않는다.

## 2026-08-20 검색 세션 보기·수집 정책 보완

- 검색어·카테고리·처음 선택한 사이트 묶음을 수집 키로 유지한다.
- 사이트 탭은 `view_sites`로 같은 스냅샷을 필터링한다. 사이트 탭 자체가 별도 검색 키를 만들지 않는다.
- 전체 검색 뒤 특정 사이트에 진입하면 저장 결과를 먼저 표시하고 `focus_sites`로 해당 사이트만 기본 160개에서 320개 후보까지 비동기 보강한다.
- 사이트 보강 응답은 첫 3페이지, 최대 90개를 백그라운드에서 미리 읽고 보강 중 사용자가 이동한 페이지를 유지한다.
- 사이트 보기·정렬·가격 범위는 페이지를 1페이지로 초기화하며 각 보기 조건의 서명된 커서를 사용한다.
- `낮은 가격`은 현재 결과 배열을 즉시 숫자 가격순으로 바꾸고 같은 SQLite 스냅샷을 다시 읽는다. 원 사이트 가격순 후보는 추가 수집하지 않는다.
- `다음 매물 더 찾기`는 정렬과 무관하게 현재 사이트의 최신 후보 창을 160개 단위로 확장하고, 표시 단계에서 현재 정렬을 적용한다.
- 저장 결과가 있으면 fresh 여부와 무관하게 먼저 응답한다. stale이면 백그라운드 갱신 토큰을 함께 반환한다.
- 회귀 계약은 `npm run search-session:contract`가 소유한다. 운영 배포 전에는 live 검색과 브라우저 흐름을 별도로 검증한다.
