# 2026-11-06

## 매물 목록 응답 지연(모바일 30초 대기)

- 증상: 모바일에서 카테고리 첫 화면이 "현재 매물을 불러오는 중입니다."에서 오래 멈춘다.
- 측정(운영, 변경 전): 첫 화면·모델 목록 0.5~0.7초, Worker 캐시 적중 매물 0.5초. 캐시가 없는 `/api/pc/listings`는 단건 기준 파워 2.4초, GPU 5.5초, HDD 11.6초였고, 여러 카테고리가 동시에 들어오면 CPU 25초·SSD 23초, 나머지는 30초를 넘겼다. 네트워크·단말이 아니라 러너 계산이 원인이다.
- 원인: `browsePcListings`는 첫 100건을 고르기 위해 카테고리 전체 매물을 읽고 행마다 구성 판정·중복 제거·사이트/모델별 개수를 계산한다. 이 동기 SQLite 계산이 러너 HTTP 스레드를 막아 다른 요청이 줄을 선다. Worker 캐시(5분, 데이터센터별)가 비면 다음 방문자가 이 계산을 다시 기다린다.
- 결정: 수집 완료마다 모든 카테고리를 미리 계산하면 러너 수집 주기만큼 계산이 늘고 아무도 보지 않는 범위까지 계산한다. 그래서 요청된 범위만 저장하고, 오래된 범위는 이전 결과를 먼저 응답한 뒤 한 번만 다시 계산한다.
- 수정:
  - `aws-runner/pc-listings-read-cache.mjs`: 첫 페이지 결과를 조회 조건별로 저장(최대 48개). 5분 이내는 그대로, 5분~1시간은 이전 결과를 응답하고 뒤에서 한 번 갱신, 1시간 초과나 처음 요청은 계산 후 응답. 동시에 들어온 같은 조건은 한 계산을 공유한다. 실패한 조건은 저장하지 않는다.
  - `aws-runner/pc-listings-browse-worker.mjs`: 전체 범위 계산을 읽기 전용 SQLite 연결의 작업 스레드 하나에서 실행한다. 작업 스레드 실패·60초 초과 시 기존처럼 HTTP 스레드에서 계산한다(가용성 우선, 잘못된 조건은 기존 400 그대로).
  - `runner.mjs`: 다음 페이지(cursor) 요청은 저장하지 않고 cursor의 기준 시각으로 계산한다. 저장된 결과를 쓸 때도 그 결과의 `as_of`로 신선도와 다음 cursor를 만든다. 응답 헤더 `x-pc-runner-cache`(HIT/STALE/MISS/BYPASS)로 경로를 확인할 수 있다.
- 표본·정체성: 계산식, 필터, 개수, 정렬은 바꾸지 않았다. 저장된 결과는 최대 1시간 전 계산일 수 있으나 방문이 있으면 5분 안팎에서 갱신된다(기존 Worker 5분 캐시와 같은 수준).
- 테스트: `npm run test:pc`, `npm run test:storage`, `npm test`. 추가 계약: 같은 조건 재요청 HIT·동일 결과, 동시 MISS 1회 계산, 오래된 범위 1회 백그라운드 갱신, 실제 파일 DB에서 작업 스레드 결과가 쓰기 연결 결과와 동일, 잘못된 조건 오류 전달.
- 반영: 미배포(운영자 승인 대기).
