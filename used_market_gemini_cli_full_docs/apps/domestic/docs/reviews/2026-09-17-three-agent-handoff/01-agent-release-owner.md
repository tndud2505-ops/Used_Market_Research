# 에이전트 1 — 게시 오류 해결·운영 배포·최종 통합 담당

## 역할

USED PICK의 유일한 운영 쓰기 담당이다. 계획만 작성하지 말고 기존 코드와 운영 상태를 인수해
게시 오류 해결, 일관된 운영 반영, 정식 배포, 최종 통합 검증까지 수행한다.
처음에는 같은 폴더의 `00-current-state-and-blockers.md`를 끝까지 읽는다.
기존 운영 담당자가 활동 중이면 먼저 결과·잠금을 인수한다. 파일이 없다는 이유만으로 동시 작업이 없다고 단정하지 않는다.

## 현재 핵심 문제

14:03 KST의 직접 조회에서 v18 정규화·실수집은 반영됐지만 정확 게시 완료 수는 0이다.
정기 게시 두 번 모두 `D1_STATS_IMPORT_HTTP_503: {}`로 실패했다.
현재 배포 gate는 `PC_PUBLICATION_NOT_RECENT`다. SSH나 Worker dry-run 거부로 분류하지 않는다.
공개 카탈로그 v4와 v18 가격 응답이 섞여 있고, 표본 있는 RAM도 대표값과 게시 ID가 없다.
'새 전체 통계 게시가 완료되지 않은 부분 반영 상태'부터 안전하게 다룬다.

## 소유 파일 및 권한

- 운영 DB/서비스/설정/실수집/게시/Worker/D1 쓰기는 이 에이전트만 수행.
- 주 소유: `aws-runner/runner.mjs`, `publish-pc-stats-runner.mjs`,
  `complete-pc-stats-publication.mjs`, `import-pc-stats-publication.mjs`, 설치·운영 스크립트.
- 주 소유: `cloudflare/worker.mjs`, `free-tier.mjs`, `public-product-stats.mjs`,
  `deploy.mjs`, `release.mjs`, `wrangler.jsonc`, 필요 migration.
- 최종 `package.json` 테스트 연결 및 통합 git 작업 담당.
- 에이전트 2의 web-backend/public 및 에이전트 3의 분류·원장 파일을 임의로 동시에 수정하지 않는다.
- 통합 계약 테스트 중 기존 `pc-publication-contract.mjs`, `aws-runner-deploy-contract.mjs`,
  `pc-service-contract.mjs`의 공유 변경은 이 담당자가 취합한다.

## 실행 순서

1. Git HEAD/변경, 현재 운영 버전, 활성 게시, 소유 잠금, 현재 PID와 명령의 정체성, 서비스, 디스크를 재확인한다.
   13:20 백업 이후 실수집 관측도 보존할 수 있는 복구 계획·새 복구 지점을 확보한다.
   이미 적용된 v18 202,242건 전체 재분류나 44개 검증 수집을 이유 없이 다시 하지 않는다.

2. `regular-publication.json`, `regular-publication-retry1.json`의 실패를 읽는다.
   Cloudflare 쪽 실패 요청 로그와 대조해 503 반환 계층을 확인한다.
   진단에는 HTTP status/content-type/request ID·CF-Ray/소요시간/제한된 비밀값 제거 본문을 남긴다.
   현재 게시기는 비JSON 오류를 `{}`로 잃을 수 있다. 토큰·전체 요청 데이터가 출력되지 않게 오류 관측성을 개선한다.
   31,149,081바이트/2,086행이라는 사실만으로 요금제·요청 한도·D1 장애를 확정하지 않는다.
   동일한 실패를 무작정 반복하지 않는다. 403/429/CAPTCHA가 나타나면 정책대로 중단한다.

3. 에이전트 3과 전체 게시 범위를 맞춘다.
   로컬 완료 게시가 0개이므로 로컬 직전 게시만 합치는 코드로는 이전 D1 범위를 포함했다고 보증할 수 없다.
   현재 D1 활성 범위 키와 새 관측 범위 키를 직접 읽어 차집합을 확인한다.
   과거 2,294행 대비 새 2,086행만 보고 가격을 삭제하거나 이전 가격을 섞지 않는다.
   필요한 범위 전체를 동일 버전·동일 기준 시각으로 다시 계산한다.

4. 필요하면 전송/처리 방식을 고친다. 게시 데이터를 분할 전송할 경우에도 최종 검증 전에는 비활성 staging에 적재하고,
   전체 ID/checksum/행 수/키 집합/구성원 추적을 통과한 뒤 한 게시 단위로 전환한다.
   부분 활성 게시를 성공이라고 처리하지 않는다. 기존 정식 gate와 복구 경계를 유지한다.
   새 Worker 코드가 게시 프로토콜에 필요한 순환 의존이 생기면 호환성 유지형 단계 전환을 검증하고 문서화한다.
   이를 핑계로 --app-only나 직접 unguarded deploy를 사용하지 않는다.

5. 실패한 job이 health last_error=null이어도 성공으로 보이지 않도록 게시 실패 상태의 관측·복구를 확인한다.
   새 통계가 준비되지 않은 동안 공개 읽기에서 버전/자료 준비 상태를 정직하게 표시한다.
   수집한 관측은 보존한다. 이전 DB 전체 복원으로 최근 관측을 잃는 롤백은 금지한다.

6. 승인된 정기 `daily-price-refresh` 실행 경로로 성공을 확인한다.
   수동으로 같은 job을 호출한 성공과 자동 스케줄에서 관찰한 성공은 따로 기록한다.
   미래 정기 주기의 성공을 추정하지 않는다. 수집 증거 부족/추가 수집은 에이전트 3의 요청을 검토해 이 담당자만 실행한다.

7. 에이전트 2·3의 수정 파일/해시/검사 결과를 취합하고 후보 소스를 고정한다.
   앱 npm test, 루트 scripts/verify.ps1, 필요한 추가 테스트, git diff --check를 최종 후보에 실행한다.
   테스트가 끝난 후보와 실제 배포 패키지의 해시를 대조한다. 다른 에이전트가 수정 중인 작업 트리를 즉시 패키징하지 않는다.
   기존 정식 cloudflare/release.mjs 및 준비 검사 절차로 Runner·Worker/UI를 반영한다.

8. 공개 일반 URL/캐시를 포함해 아래 기존 검증을 실행한다. 독립 브라우저 검사는 에이전트 2,
   통계/API 감사는 에이전트 3의 검토를 받되 최종 합격 취합은 이 담당자 책임이다.

```text
node tmp/pc-resume-full-audit.mjs --after
node tmp/pc-live-v18-browser.mjs
```

v18보다 새 버전이 필요했다면 검사 기대값을 검증된 릴리스 manifest로 명시적으로 맞춘다.
버전 검사를 제거하거나 실패 항목을 통과하도록 약화하지 않는다.

## 사용자에게 요청할 외부 조치

실제 실행이 권한/계정/플랫폼 차단을 반환할 때만 아래 형식으로 전달한다.
- 실행 위치와 명령 또는 요청 경로(비밀값 제외)
- KST 시각, exit/HTTP status, 오류 원문, 증거 파일
- 코드 결함/준비 조건/도구 정책/클라우드 인증 중 어느 계층인지와 확정 여부
- 사용자가 해야 하는 최소 한 가지 조치, 영향과 복구 방법

현재 알려진 것은 import 요청 503이지 키 만료나 sudo 부족이 아니다.
사용자에게 보안 전체 해제·키 공개·유료 전환을 근거 없이 요구하지 않는다.

## 산출물과 완료 조건

역할 결과 파일 `01-agent-release-owner-result.md`에 다음을 기록한다.
- 503 원인: 확정/미확정 및 해결 전후 근거
- 운영 DB/코드/서비스/Worker/D1 게시 복구 지점과 최근 관측 보존
- 배포 시각·소스 commit/패키지 hash·Worker ID·카탈로그/정규화 버전
- 게시 ID/checksum/키 집합/행 수/게시 시각/구성원 추적 대조
- 정상 수집·게시 실제 실행 결과와 남은 자동 스케줄 관찰
- 전체 완료 판정표와 에이전트 2·3의 검증 결과

본 작업 소스·테스트·문서만 선별 커밋한다. 운영 로그·JSON·DB·비밀값은 제외한다.
화면이 열리거나 dry-run이 통과했다는 이유만으로 배포·가격 시스템 완료라고 하지 않는다.
